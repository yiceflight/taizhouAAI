# 无人机状态与巡飞调度

顶部右侧显示后台持久化任务的简要状态与“查看详情”：待命、倒计时、准备中、待人工确认、提交中、起飞请求已提交、结果待核查、禁飞仅记录、取消或失败。详细操作与回执位于监测卡片下方“巡查任务”模块；顶部入口滚动定位到该模块。失败统一提示“起飞未完成 · 待人工核验”，不从填写校验回执推断具体设备故障。秒级倒计时只负责显示，调度在 Rust 后台执行；关闭主窗口不会停止后台，完全退出后重启会取消旧倒计时，不补发过期起飞任务。

巡查任务模块统一保留标题右侧「查看任务 →」入口，操作行不再重复显示「查看任务详情」，也不提供「查看实时监测」。待核查、已提交和执飞中保留「到司空核查任务」；没有可用菜单项时不显示「更多」。

没有待处理任务时，有效 K⁺ 或 PM2.5 超过当前设置阈值会将右上角控件显示为与图表超标点相同的红色（`#b44831`）。手动模式显示“需要执行任务”和“立即执行任务”按钮；工作环境未就绪时禁用起飞。司空判定“不宜飞行”时显示“手动强制起飞”，打开弹窗后必须完成现场复核、勾选确认，再点击“确认强制起飞”，仅为本次手动任务覆盖系统天气判断。自动任务始终遵守天气门控。自动起飞任务创建后显示真实倒计时与“取消任务”，取消入口不受其他操作忙碌状态影响。已取消或已提交的任务仍保留其实际结果，不因当前超标重新显示待执行提醒。

起飞准备失败的任务保留手动入口，司空判定适合飞行时显示“重新发起任务”，判定不宜飞行时显示“手动强制起飞”；气象数据不可用或已过期时禁止发起，明确天气不宜飞行仍可在现场复核并强制发起；两者均需要弹窗确认，无需先归档。后台只接受与当前失败任务 ID 匹配的重新发起请求，保留原失败快照与原小时去重标记，并创建独立的手动任务。准备中、提交中、已提交、结果待核查及执飞中的任务不能被覆盖。强制起飞的现场确认时间保存在本次任务中，不修改全局设置，也不继承到下一次任务或客户端重启后的重试。

## 任务详情模块交互规则

- 每个阶段突出一个下一步操作：倒计时/准备中可取消；待人工确认到司空核对起飞；已提交、待核查或执飞异常到司空核查；执飞中到司空核查；巡飞结束核对资料并生成报告。提交中仅展示等待状态与任务详情，不提供重复起飞或归档操作。
- 准备失败提示人工核验电量、设备和平台任务，将原始回执放入可展开详情；不把回执等同于已确认的设备故障，不以当前天气替换此前回执。未知原因不编造，详情按来源标注为触发数据时间（自动任务）或任务创建时间（手动任务）。
- 失败时主操作为重新发起（仅司空“不宜飞行”时保留现场复核后的手动强制起飞），辅以「查看失败详情」和「更多」。详情及重新发起确认说明创建新手动任务、保留原失败记录，无需先归档。
- 失败任务的司空辅助入口收进「更多」，仅打开页面，不提交起飞。失败任务可选择「暂不执行本次任务」，二次确认后收起本次失败提醒；不关闭自动巡查，不清除自动任务的原小时去重。确认期间任务 ID 或状态变化时阻止操作。
- 已提交、结果待核查、暂停及执飞中不显示结束处理入口，继续状态核查。待人工确认的真实任务和执飞异常也持续只读核查；两者在「更多」中提供「核查后结束任务」，须勾选确认司空原计划已结束或已取消、没有待执行或正在执行的任务。结束仅解除本地占用，不取消平台计划，不标记飞行成功，不触发新的起飞。填写演练提供独立「结束演练」，不进入真实任务轮询。巡飞结束突出报告入口，新的手动任务入口放到「更多」。保存报告时不展示新任务入口。
- 待人工确认（真实任务）、执飞异常、已提交、结果待核查、暂停及执飞中的任务提供「刷新状态」，与后台自动核查共用只读查询并串行执行；不填写或提交计划。模块展示最近核查时间及失败原因，失败后可再次刷新。回执必须匹配当前事件与计划名；查询到「待执行」后从待人工确认、执飞异常或待核查转为已提交，继续跟踪并禁止重复起飞。
- 不提供单独的核查后重发入口。原草稿明确返回天气阻飞且未继续执行时，更新为 `not_flown` 并保留回执，同时保留原草稿的只读核查；顶部和任务模块提示用户到司空自行决定是否继续，并提供按钮切换到对应 Chrome 页面。用户在司空点击继续后，后台可将同一任务更新为已提交或执飞中；同一来源小时不会自动重试，新的有效超标小时可按当前天气重新调度。手动与后台刷新查不到任务时均保留 `uncertain` 占用并继续核查；列表缺行不是未起飞证据，不因换小时或刷新解除。已提交、待执行、执飞中和暂停同样保留占用，直到获得明确结果。

## 配置和触发

- 禁飞时间默认每天北京时间 05:00–08:00，设置中可增删多段，支持跨午夜。数据小时或当前执行时间落在时段内时，超标只保存带原因的 `restricted` 记录，重复同步不重复记录；禁飞结束后不补飞该小时。倒计时跨入时段或提交前配置变化同样会拦截。仅停止本应用尚未提交的起飞，不改动平台定时任务或已提交、待核查、正在执飞的任务。手动天气覆盖不能绕过当前禁飞时段。

- 需要满足 `bridge-config.json` 最低版本要求的浏览器插件。有效 K⁺ 或 PM2.5 超过阈值后始终创建一次巡查计划，执行方式只由「起飞前人工确认」决定：开启时由工作人员确认起飞，关闭时按延迟自动执行。旧版本遗留的自动巡查开关不再参与判断。
- 阈值、起飞延迟、人工确认共用 `workspace_settings`，无第二套延迟设置。默认 K⁺ 阈值 1.0、PM2.5 阈值 30，自动起飞延迟 5 分钟，需要人工确认；仅关闭人工确认时启用延迟，支持 0–1440 分钟。
- 成功同步/首次开始工作后，最近一条非未来且不超过 3 小时、至少有一项有效值的小时数据中，K⁺ 严格超过 K⁺ 阈值或 PM2.5 严格超过 PM2.5 阈值，并且工作环境与天气通过时，按执行方式创建倒计时或直接准备计划。PM2.5 默认阈值为 30 μg/m³；尾部暂时缺测的小时不遮蔽上一条至少有一项有效值的小时数据。
- 按监测来源小时独立触发，持续超标无需先恢复正常。每个已处理小时持久去重，重复同步、修订、重启均不重复提交；旧 `flight_episode` 时间仅抑制对应及更早小时。上一任务完成、明确未起飞、取消或经人工确认结束后，下一有效超标小时可正常调度。尚未结束或结果不明的任务继续阻塞重复起飞。没有任何有效 K⁺/PM2.5、或数据未来、过期时不触发，也不回放离线期间的历史超标小时。
- 每个自动事件保存 `sourceHour`，并结合该小时的历史事件和去重回执判断是否已经处理；手动事件也绑定当前最近有效小时，但不占用该小时的自动去重位，所以同一小时可以保留多条手动起飞行为。
- 自动、手动及演练任务在发送起飞请求前失败（`failed`）时，统一在下一有效来源小时释放占用。同一小时的重复同步不重试，也不因电脑时钟跨整点而重放旧小时。收到比失败任务来源小时（手动/演练按创建时间所在小时）更新、非未来且不超过 3 小时的有效 K⁺ 或 PM2.5 数据后，在同一事务内将原失败快照保存到 `flight_history:<id>`、清除当前失败占用与本轮超标标记，保留原小时去重记录、错误和创建天气。新数据正常则恢复待命；仍超标则按当前天气、人工确认和延迟重新调度；处于禁飞时段则只记录。天气不通过时不消耗新小时，后续同步可以重新判断。缺测、过期、未来数据不解除失败；准备中、待确认、提交中、已提交、结果待核查、暂停及执飞异常不能按小时清除。
- 延迟在创建事件时固定；修改延迟用于下一次任务。关闭人工确认时，自动任务填写完计划后，司空页面右侧会显示字段核对面板；所有字段回读通过后固定等待 30 秒。倒计时期间可在面板点击“取消本次作业”，取消会落到客户端持久任务状态并阻止提交。倒计时结束后才允许唯一一次最终「确定」点击。人工确认模式仍只到 `ready`，不自动点击。
- 立即执行任务无需 K⁺ 或 PM2.5 超标或存在有效监测数据，但仍需工作环境、实时天气回执和航线配置通过：固定模式使用手动选择的司空航线，高级模式在起飞前按实时机场风向规则选择航线；明确人工确认的“手动强制起飞”覆盖本次天气判断，若司空随后弹出阻飞提醒则交由工作人员在司空页面自行确认。填写演练始终不提交，也不能覆盖天气门控。
- 未出现有效 K⁺/PM2.5 超标预警时，顶部的“立即执行任务”先弹窗确认，展示当前机场天气、风速、阵风、降水，以及 K⁺、PM2.5 浓度、阈值和数据时间。缺测、过期或时间异常明确提示无法判断；取消不会发起任务。弹窗统一使用“确认执行任务”，并说明巡飞后还需核对资料、生成报告。确认时重新检查工作环境、天气与已有任务，等待期间条件变化会阻止起飞。

## 取消、提交和恢复

- 倒计时和计划准备阶段可以取消；取消不被正在执行的数据同步阻塞。原生状态锁保证取消和提交只有一方成功。
- 进入提交阶段后由司空处理飞行操作，已提交、结果待核查及执飞中的任务不提供归档入口，继续后台核查；客户端不将收起提醒当成取消飞行。
- `dji-prepare` 负责填写并回读固定字段；自动提交路径的 `dji-submit` 独立校验真实任务、原草稿、固定项目、航线、机场和全部配置，等待 30 秒后再次回读且不覆盖人工修改，再点击唯一最终确定一次。人工确认和填写演练不下发 `dji-submit`。不会自动处理未知二次弹窗。
- 插件 v0.7.10 在最终确定后只读检测司空二次弹窗，将正文（如天气阻飞、设备名、在线天气风速）回传为具体回执，不继续点击“执行”。首次提交若明确返回“司空平台天气阻飞：…；未继续执行”，客户端立即保存为 `not_flown`，保留原小时去重和历史回执，并保留该事件的状态核查；界面提示工作人员到司空自行确认，点击入口会将对应 Chrome 计划标签页切换到前台。用户在司空继续执行后，后台状态轮询可更新同一事件；新的有效超标小时仍可按当前天气重新调度。已进入待核查的任务仍检查同事件、同计划名的原草稿，取得同样的明确阻飞回执时使用同一处理；其他错误保持待核查且不重试提交。客户端天气源与司空天气源分别保留，客户端天气通过不能代表司空允许执行。
- 插件在尝试提交前持久化事件标记，重复同一事件会拒绝。超时、回执不匹配、提交中重启均进入待核查，不自动重试。
- 只有跳转回指定项目计划列表并读到唯一计划名才显示请求已提交。插件 v0.7.5 随后在独立的司空计划列表标签页轮询同名任务：检查「未完成」和「已结束」页，明确显示「执行中」才更新为正在执飞，「执行成功 (9/9)」等成功状态才自动恢复待命；暂停、挂起、部分执行、失败和终止保留待核查并继续轮询，后续明确执行结果仍可更新；异常也可经人工核查后结束本地处理。客户端重启后继续核查仍未归档的已提交任务。网页缺行、登录失效或状态不唯一时维持原状态并在巡查任务中显示核查原因，下一轮继续尝试，不推断飞行结束。这里显示的是司空计划执行状态，不是飞行器遥测。
- Word 快报在实际飞行结束、媒体上传完成后自动生成，失败后自动重试；人工核对和重新生成入口保留。无可飞数据报告在关联采样恢复后自动补全为新版本，旧文件保留，列表只展示当前版本。飞行结束不等于报告已生成。

## 任务历史与结束处理

- 自动新任务、手动新任务、失败重试和禁飞记录替换当前任务前，统一在同一 SQLite 事务内保存旧事件。新任务写入失败时，历史写入和当前状态同时回滚。
- 「暂不执行本次任务」「核查后结束任务」「结束演练」保留原状态、错误回执、天气证据，并记录结束处理时间 `resolvedAt`；任务列表显示「已结束处理 · 原状态」。不会用 `dismissed` 覆盖原来的执行结果。
- 后端结束命令同时校验事件编号、弹窗打开时的状态和确认标记。已提交、待核查、正在执行、暂停及正在提交的任务不能通过结束命令解除占用；界面状态变化时禁用原确认操作。
- 经人工确认结束真实待确认/异常任务后，仅抑制对应来源小时；新小时重新判断。结束演练不消耗自动巡查小时，准备失败保留原小时去重。
