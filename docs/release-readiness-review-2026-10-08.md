# 正式发布前功能审查（2026-10-08）

结论：现有代码具备内部试用的主体能力，但不建议直接作为完整自动监测巡飞产品正式交付。至少应修复自动巡飞配置断链、缺测处理和飞行完成后的再次执行问题，并明确人工确认与 AI 功能的真实范围。

本次审查基于当前工作区，包括未提交修改与新增文件。检查了 React 界面、Rust 后台、Chrome 插件、SQLite 保存、Word 快报和发布工作流。没有修改业务实现，也没有提交计划、触发飞行或发布安装包。检查时 1450、14520、14521 均未发现监听服务，本次没有启动或重启客户端；因此不能视为当前原生客户端与真实业务账号的端到端验收。

## 已确认的功能问题

### 1. P1：新安装环境无法通过界面启用自动巡飞

- 位置：`src-tauri/src/flight.rs:56`、`:105`、`:275`；`src/components/SettingsDialog.tsx:58`。
- 自动创建任务要求 SQLite 中 `flight_launch_enabled=true`，默认关闭；只有 `set_flight_enabled` 写入这一配置。
- 生产前端没有调用该命令。设置中的“起飞前人工确认”和延迟只保存 `workspace_settings`，不会开启自动巡飞。
- 因此关闭人工确认后，界面承诺“超标后开始计时、延迟结束自动起飞”，新安装环境实际不会创建倒计时；默认人工确认模式也不会自动填写计划。
- 建议：明确区分“启用自动巡查”和“提交前人工确认”，显示实际生效状态；如果首发仅支持手动巡查，应同步收缩界面承诺。
- 验收：全新数据库通过界面配置后，有效超标、天气通过、三站就绪时创建且只创建一次任务；关闭后取消未提交自动任务；重启保持配置且不重放旧倒计时。

### 2. P1：缺测小时被裁掉，旧超标数据可能继续参与判断

- 位置：`extension/src/jiangsu.js:68`；`src-tauri/src/monitoring.rs:165`；`src-tauri/src/flight.rs:94`。
- 归一化只保留截至最后一个非空值的记录。直接执行当前函数确认：08:00–10:00 全部缺测返回 `[]`；08:00=1.5、09:00/10:00 缺测，只返回 08:00。
- Rust 即使收到空数组，也推进 `query_through` 并更新 `last_success`。界面看不到这些缺测小时；超过 48 小时回查范围后，不会再自动补查这些时间。
- 后台按数据库最新一条判断超标。当之后的缺测记录被丢弃且旧值仍在三小时有效期内时，会继续把旧超标值作为最新可用判断。这也会影响手动按钮的超标提示。
- 建议：区分未来占位与已经发生的缺测，保留过去小时的 null；区分查询成功、缺测和有效数据到达；提供可恢复的补采路径。
- 验收：全缺测、尾部缺测、有效零值、未来占位、之后补回数据、跨 48 小时修订均有明确结果；最新缺测时不沿用更早超标值触发新任务。

### 3. P1：飞行完成后再次手动执行被界面锁死

- 位置：`src/components/DroneStatus.tsx:27`；`src/components/ManualLaunchButton.tsx:34`；`src-tauri/src/flight.rs:67`。
- 顶部状态和 Rust 都将 `completed` 当作已结束，显示“待命”和执行入口；按钮组件却只将 `dismissed/canceled` 排除在活动任务之外。
- 用当前组件实际渲染确认：状态为“无人机 · 待命”，按钮输出仍带 `disabled`。
- 完成态又不显示“归档提醒”入口，用户无法通过这条界面路径解锁下一次手动任务。
- 建议：统一终态判定，完成后允许再次手动执行，并保留上次任务待生成报告的记录。
- 验收：完成 → 再次手动执行可用；执行中、暂停、待核查仍阻断；天气和工作环境仍有效门控。

### 4. P2：人工确认设置的适用范围与界面说明不一致

- 位置：`src-tauri/src/flight.rs:64`、`:130`、`:303`；`src/components/ManualLaunchButton.tsx:58`；`src/components/SettingsDialog.tsx:58`。
- `require_manual_confirmation` 仅对 `source=auto` 生效。手动入口产生 `source=manual`，会填写后走 30 秒核对倒计时和自动提交。
- 当前 K⁺ 超标时点击“立即执行任务”不会先弹确认框，而设置仍显示“开启：由工作人员确认后起飞”。操作者容易把它理解成先填写、之后再确认提交。
- 这不表示用户没有点击执行授权；问题在于界面没有说明该点击是否已经视为最终人工确认，以及设置不覆盖手动入口。
- 建议：统一设置语义，或明确标注“仅自动超标任务适用”，并在手动入口清楚说明自动提交行为。
- 验收：人工确认开启/关闭 × 手动/自动 × 超标/无超标的行为、按钮说明与实际提交路径一致。

### 5. P2：AI 火点分析显示开启，实际未执行

- 位置：`src/components/SettingsDialog.tsx:65`；`src-tauri/src/flight_report.rs:502`。
- 火点开关固定 `aria-checked=true` 且禁用，既不保存配置也不调用识别能力；报告正文明确说明未执行 AI 火点识别。
- 界面会让用户以为报告已经包含自动火点判读。
- 建议：首发明确显示“暂未提供，需要人工判读”，或隐藏预留开关；如果 AI 属于承诺功能，需要补齐输入、分析、结果、失败状态和人工复核。
- 验收：界面不会把占位状态显示成已经生效的分析服务，报告与产品说明一致。

### 6. P2：本地巡查任务没有完整历史台账

- 位置：`src-tauri/src/flight.rs:44`、`:49`、`:303`；`src/lib/flightReport.ts:24`。
- 本机只保存单个 `flight_event`，新任务覆盖旧任务；巡查列表由当前可飞查询、已生成报告和这一个本地事件合成。
- 尚未进入可飞或未生成报告的失败、取消、归档任务会在后续任务创建后失去本地列表记录；本次运行读取的可飞任务也仅在 React 内存中保存。
- 建议：按事件 ID 保存任务历史与状态变化，关联可飞任务 ID、司空计划和报告；失败、取消及归档也可追溯。
- 验收：连续多次任务、取消、失败、归档、离线和客户端重启后，能查到完整本地处理结果。

### 7. P2：“重新验证”存在提前返回旧结果的窗口

- 位置：`src-tauri/src/readiness.rs:186`、`:349`。
- 自动检查已经开始但 UI 尚未获知时，人工重新验证可能进入 `refresh` 的忙碌分支，直接返回成功，不等待当轮检查结束，随后返回旧缓存。
- 建议：复用并等待当前检查，或明确返回“检测进行中”，完成后再报告结果。
- 验收：自动与手动检测重叠时，不提前宣告完成；返回结果对应已完成的检查。

### 8. P2：状态刷新存在覆盖和错误恢复问题，隐藏后仍持续轮询

- 位置：`src/lib/useWorkspace.ts:14`、`:21`；`src-tauri/src/monitoring.rs:69`、`:244`。
- 每两秒刷新，没有请求序号或在途互斥；较慢的旧结果可覆盖较新的状态。成功轮询仅清除 `pollError`，旧操作错误可能在自动恢复后继续显示。
- 关闭窗口隐藏后，轮询没有显式暂停逻辑；每轮 `get_monitoring` 都重新打开数据库并执行 WAL/建表初始化。实际隐藏时计时器频率仍取决于原生 WebView 行为，本次未测量资源消耗。
- 建议：让最新请求结果优先生效，按错误来源清理恢复提示；可见性控制 UI 轮询，后台监测与调度继续由 Rust 负责。
- 验收：慢请求、断连恢复、取消与普通操作并发、托盘隐藏恢复均显示最新状态，恢复后不残留已解决错误。

### 9. P2：安装更新没有与业务操作协调

- 位置：`src/components/UpdateBanner.tsx:81`、`:114`；`src/lib/appUpdater.ts:39`；`src/App.tsx`。
- 更新组件只检查自身下载状态，不读取准备、提交或报告采集/保存状态；安装会重启客户端。
- 若用户在计划准备、提交或照片采集中点击更新，操作可能中断；现有重启恢复能标记部分待核查任务，但不能代替业务完成。
- 建议：允许后台下载，安装重启前检查当前操作并展示具体影响，关键写入或提交期间延后安装。
- 验收：任务提交、报告资料采集及保存过程中不直接重启；空闲安装完成后数据和插件连接正常恢复。
