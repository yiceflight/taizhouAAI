# 自动巡查“同一小时不丢失”加固

现象：自动模式下某些小时完全不飞，记录只有一条含糊的“失败”，下一小时照常触发。复核代码后确认真实原因不止一个，且互相掩盖。

## 已定位的原因

1. **填写超时被统一定为唯一超时**：`fillFlightPlan` 原先只有一个 55 秒总预算，慢页面（航线库分页、设备卡片、核对面板）只能整体超时，日志里看不出卡在哪一步。现在按步骤计时（打开表单、任务类型、航线、设备、参数、核对、提交），超时消息带步骤名。
2. **“未发送”与“可能已发送”无法区分**：提交结果原先只有一条笼统错误。现在每个失败都带 `sent` 标记；服务端只把明确的“未发送起飞请求”视为可重试，Chrome 连接中断、回执丢失一律视为**可能已提交**，绝不重放。
3. **失败后同一小时永久作废**：`observe` 只在新小时才放行，自动模式下一次填写失败就丢掉该小时的全部飞行。现在失败事件带 `retryAt`，由 `tick` 在同一超标小时内有限重试。
4. **倒计时期间关客户端**：倒计时中退出/更新后，`claim_due` 会在下次启动时直接按旧回执起飞，或（时间已过时）静默丢弃。现在 `launchAt` 早于本进程启动时间的自动任务一律改为重新准备并重新核对，不再按无人看守的计时器起飞。
5. **PM2.5 正常小时遮住钾离子超标**：`latest_trigger` 原先只取“最新一行”，新增的 PM2.5 正常小时会遮住仍在时效内的钾超标。

## 重试的边界

- 只对**自动**任务、且未开启人工确认时重试；预览、手动任务从不自动重试。
- 只对**同一 sourceHour** 且该小时仍然是“最新超标小时”时重试；阈值上调、小时过期、出现更新的正常小时即停止。
- 次数上限 3 次，持久化在事件上，重启不清零；每次重试都是新的准备流程，重新经过就绪检查、禁飞时段、天气与数据时效。
- 可重试的前提是**没有任何起飞请求被发送**：失败可能发生在提交之后（`uncertain`、提交回执不匹配、连接中断）时绝不自动重试，仍由人工到司空核查。
- 人工重新发起（`begin_manual_with_weather`）会清除 `attempt`/`retryAt`，重试的收据随之作废。

## 验证

- Rust `flight` 模块 85 项通过，新增 4 项：有限次重试并保留失败回执、超标小时变化后停止、`uncertain` 与人工模式不重试、倒计时被重启中断后重新核对。
- 插件 Node 测试 233 项通过；新增提交失败 `sent` 标记用例（明确未发送 vs 连接中断不可断言未发送）。
- TypeScript 检查通过；UI 测试已修正为符合产品规则：自动采集期间不允许打开报告弹窗，完整 UI 测试 276 项通过。
- 插件版本 0.7.66 → 0.7.67，`bridge-config.json` 最低插件版本同步为 0.7.67。
